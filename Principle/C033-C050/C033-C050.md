## 为什么分阶段？

vLLM 的 FlashAttention 生态有 9 层架构：

```
Layer 1: Scheduler → build_attn_metadata → CommonAttentionMetadata
Layer 2: ForwardContext.set() / get() 注入
Layer 3: Attention.forward() → unified_attention_with_output dispatch
Layer 4: AttentionBackend / AttentionImpl / AttentionMetadataBuilder ABC
Layer 5: FlashAttentionBackend / TritonAttentionBackend 实现
Layer 6: Kernel ops (reshape_and_cache, decode, prefill, unified, chunked)
Layer 7: AttentionBackendEnum + selector + registry
Layer 8: init_attn_backend + init_kv_cache + AttentionGroup
Layer 9: KV cache physical layout (NHD vs HND stride_order)
```

Layer 4 (backend ABC) 和 Layer 7 (registry) → C042 已规划。
Layer 2 (ForwardContext) 和 Layer 3 (Attention dispatch) → C041 已规划。
Layer 1 (build_attn_metadata) + Layer 8 (init chain) → C044 扩展。

**C043 聚焦 Layer 5 + Layer 6 + Layer 9：backend impl + kernel ops + physical layout。**

## C043-A — FlashAttentionBackend 完整实现

目标：理解 FlashAttention 的 KV cache layout 和 paged attention 调用。

```
v1/attention/backends/flash_attn.py:

  FlashAttentionBackend:
    get_kv_cache_shape(num_blocks, block_size, num_kv_heads, head_size):
      → (num_blocks, num_kv_heads, block_size, 2 * head_size)
      # K/V 打包: head_size 在最后一维拼在一起
    get_kv_cache_stride_order():
      → (0, 2, 1, 3)
      # 逻辑 (N, H, B, D) → 物理 (N, B, H, D)
      # N=num_blocks, H=num_kv_heads, B=block_size, D=2*head_size

  FlashAttentionMetadataBuilder.build(common_attn_metadata):
    → FlashAttentionMetadata
       num_actual_tokens, max_query_len, query_start_loc,
       max_seq_len, seq_lens, block_table, slot_mapping,
       causal, sliding_window

  FlashAttentionImpl.forward(layer, query, key, value, kv_cache, attn_metadata, output):
    # 1. 拆分 KV cache: transpose(1,2) → (N, B, H, 2*D) → split(head_size)
    key_cache, value_cache = kv_cache.transpose(1, 2).split(head_size, dim=-1)

    # 2. 调用 FlashAttention (cu_seqlens_q 支持 ragged batch)
    flash_attn_varlen_func(
        q=query, k=key_cache, v=value_cache, out=output,
        cu_seqlens_q=query_start_loc,   # ragged batch 索引
        seqused_k=seq_lens,             # 每个 request 的有效 KV 长度
        block_table=block_table,         # paged attention page table
        max_seqlen_q, max_seqlen_k,
        causal, softmax_scale, window_size,
    )

  FlashAttentionImpl.do_kv_cache_update(layer, key, value, kv_cache, slot_mapping):
    key_cache, value_cache = kv_cache.transpose(1, 2).split(head_size, dim=-1)
    reshape_and_cache_flash(key, value, key_cache, value_cache, slot_mapping, ...)
```

核心理解点：
- KV cache shape `(num_blocks, num_kv_heads, block_size, 2*head_size)`：K/V 打包存储
- Physical layout `(0,2,1,3)` → `(num_blocks, block_size, num_kv_heads, 2*head_size)`：为什么需要 stride_order
- `flash_attn_varlen_func` 的 `cu_seqlens_q` 参数支持 variable-length ragged batch
- `block_table` 让 FlashAttention kernel 通过 page table 间接索引 KV cache
- `do_kv_cache_update`：prefill 后将 K/V 写回物理 cache

## C043-B — TritonAttentionBackend

目标：理解 Triton 如何通过 tiling 实现 paged attention kernel。

```
v1/attention/backends/triton_attn.py:

  TritonAttentionBackend (与 FlashAttn 共享 kv_cache_shape + stride_order)

  TritonAttentionImpl.forward(layer, query, key, value, kv_cache, attn_metadata, output):
    key_cache, value_cache = kv_cache.transpose(1, 2).split(head_size, dim=-1)
    unified_attention(
        q=query, k=key_cache, v=value_cache, out=output,
        cu_seqlens_q, max_seqlen_q, seqused_k, max_seqlen_k,
        softmax_scale, causal, window_size, block_table, ...
    )
```

```
v1/attention/ops/triton_unified_attention.py:

  @triton.jit
  def unified_attention(q, k, v, out, cu_seqlens_q, max_seqlen_q,
                        seqused_k, max_seqlen_k, block_table, ...):

    核心 tile loop (prefill 2D 模式):
      pid = tl.program_id(0)
      batch_idx = find_seq_idx(pid // num_queries_per_program, cu_seqlens_q)
      q_tile = load Q[batch_idx, :, :] → SRAM

      for kv_block_idx in range(num_kv_blocks):
        block_id = block_table[batch_idx, kv_block_idx]
        k_tile = load k_cache[block_id, :, kv_block_offset:kv_block_offset+BLOCK_KV, :]
        v_tile = load v_cache[block_id, :, kv_block_offset:kv_block_offset+BLOCK_KV, :]
        S = q_tile @ k_tile^T * softmax_scale
        P = softmax(S)  # online softmax
        O += P @ v_tile

      store O → output

    3D decode 模式:
      增加 pid_z 维度做 segmented parallel softmax
      各 segment 独立计算 softmax，最后 reduce_segments 合并
```

核心理解点：
- 2D kernel（prefill）vs 3D kernel（decode）：为什么 decode 需要 segmented softmax
- `block_table[batch_idx, kv_block_idx]` → 在 Triton kernel 内通过 page table 间接索引 KV cache
- 与 FlashAttention 的关键区别：Triton 是开源的 Python→PTX kernel，FlashAttention 是闭源 CUDA kernel
- online softmax 在 tiled attention 中的实现（same as flash_attention_tiled 教育性 kernel）

## C043-C — PagedAttention Kernel Ops

目标：理解先有 backend-impl，再有 kernel ops。理解 KV cache 的物理读写操作细节。

```
v1/attention/ops/
  triton_reshape_and_cache_flash.py:
    reshape_and_cache(K, V, k_cache, v_cache, slot_mapping):
      将 prefill 产生的 K/V 写入物理 KV cache
      slot_mapping[i] = block_id * block_size + offset_in_block

  triton_decode_attention.py:
    decode_attention_fwd(Q, k_cache, v_cache, O, req_to_token, b_seq_len, ...):
      解码时从物理 KV cache 读取 + attention 计算 (split-KV 策略)
      每个 request 只有 1 个 query token, 读取全部 history KV

  triton_prefill_attention.py:
    context_attention_fwd(Q, K, V, O, b_start_loc, b_seq_len, ...):
      Prefill 阶段的标准 attention (Q/K/V 都在内存, 不需要 KV cache)
      多个 query token 对全部 prompt token 做 attention

  chunked_prefill_paged_decode.py:
    chunked_prefill_paged_decode(...):
      融合 chunked prefill + paged decode, 单 kernel 处理两种模式

  flash_attention_tiled.py:         # ← C043 扩展, 已添加
    Triton tiled attention 教育性 kernel (不替代 vLLM op)
    理解 online softmax + O(N²)→O(N) memory + recompute instead of store
```

核心理解点：
- `reshape_and_cache` 的 slot_mapping 机制：`(block_id, offset)` → 一维 slot ID
- `decode_attention_fwd` 的 split-KV 策略：将 KV cache 分片并行读取
- `context_attention_fwd` vs `decode_attention_fwd`：prefill 是 dense matrix 运算，decode 是 vector-matrix
- `chunked_prefill_paged_decode`：一个 kernel 内同时处理 prefill tokens 和 decode tokens

核心理解点：
- `O(N²)` memory → `O(N)` 的原因：逐 block 计算 softmax，不存储完整 attention matrix
- online softmax：running max + running sum 保持数值稳定
- SRAM vs HBM：tile 加载到 shared memory，recompute instead of store

## C044-A — KV Cache 初始化链

对应 vLLM `v1/worker/gpu/attn_utils.py`。

新增/扩展：
```
v1/worker/gpu/attn_utils.py:

  init_attn_backend(kv_cache_config, vllm_config, device):
    Phase 1: 发现所有 Attention 层
            → 按 (backend_cls, kv_cache_spec, num_heads_q) 分组
            → AttentionGroup(backend, layer_names, kv_cache_spec, metadata_builders)
    Phase 2: 为每个 group 选择兼容的 kernel block size
    Phase 3: 为每个 group 创建 AttentionMetadataBuilder

  init_kv_cache():
    backend.get_kv_cache_shape() → 逻辑形状
    backend.get_kv_cache_stride_order() → 物理布局 (0,2,1,3)
    bind_kv_cache(attention_modules) → 将 tensor 绑定到每个 Attention.kv_cache

  build_attn_metadata(attn_groups, num_reqs, num_tokens,
      query_start_loc, seq_lens, block_tables, slot_mappings, ...):
    for each KV-cache group:
      CommonAttentionMetadata(query_start_loc, seq_lens,
          num_reqs, num_actual_tokens, max_query_len, max_seq_len,
          block_table_tensor, slot_mapping, causal, positions, ...)
        → builder.build(common_attn_metadata)
          → FlashAttentionMetadata / TritonAttentionMetadata
    → dict[layer_name → backend_metadata]

  build_slot_mappings_by_layer(...):
    → dict[layer_name → slot_mapping]
```

核心理解点：
- `AttentionGroup` 如何将同一 `(backend, kv_cache_spec)` 的层分组
- `bind_kv_cache` 如何让每个 Attention 层持有自己的 KV cache view
- `CommonAttentionMetadata` → `backend_specific_metadata` 的转换链
- `block_tables.gather_block_tables` + `compute_slot_mappings` 如何从 request-level block IDs 生成 per-token slot mapping
