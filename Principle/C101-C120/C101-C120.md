目标：将 C081 MoE + C082 EP 扩展到 Data Parallel——token batch 维度切分，多 GPU 各自处理自己的 batch，通过 wave 协调同步。这是理解 DeepSeek-V3 / Mixtral 多节点部署的核心。

核心实现：
```python
# v1/engine/coordinator.py

class DPGroup:
    """管理 DP rank 间的 batch 分配与 wave 同步。

    参考 vLLM: DPEngineCoreProc._has_global_unfinished_reqs()

    通信模式:
    - 每个 DP rank 独立运行 EngineCore step() loop
    - 每 N step: dp_all_gather_reqs() 同步全局未完成请求数
    - 全局无未完成请求 → 进入 idle (不再轮询)
    """
    def __init__(self, dp_size, dp_rank):
        self.dp_size = dp_size
        self.dp_rank = dp_rank
        self.sync_interval = 32  # 每 32 step sync 一次

    def has_global_unfinished_reqs(self, local_unfinished: int) -> bool:
        """All-reduce 所有 DP rank 的 unfinished count。
        任何一个 rank 有 unfinished → 继续 step loop。
        """
        tensor = torch.tensor([local_unfinished], device="cuda")
        torch.distributed.all_reduce(tensor, group=self.dp_group)
        return tensor.item() > 0

class WaveScheduler:
    """将 request batch 分配到各 DP rank。

    策略:
    - 同一 wave: 所有 rank 接收相同的 request list
    - 每个 rank 独立选择自己处理的 requests
    - 保证同一 wave 内所有 rank 同时结束 → 下一 wave 同步开始
    """
    def __init__(self, dp_size, dp_rank):
        self.wave_id = 0

    def select_requests(self, all_requests: list, dp_rank: int) -> list:
        """DP-aware request selection: 根据 dp_rank 分配 requests。
        默认 round-robin: rank_i 处理 requests[i::dp_size]。
        支持 data_parallel_rank 显式指定。
        """
        return all_requests[dp_rank::self.dp_size]
```

改动：
```
v1/engine/core.py         # step_with_batch_queue() 增加 DP-aware 路径:
                            #   每 32 step: dp_all_gather_reqs() → 全局无请求 → idle
                            #   参考 vLLM DPEngineCoreProc.run_busy_loop()
distributed/parallel_state.py  # 增加 get_dp_group()
```

能力：
- DP=2: token batch 切分到 2 GPU，每 GPU 独立 step loop
- Wave synchronization: 同步 global unfinished count 决定是否继续
- DP × EP composition:
  ```
  DP=2, EP=2 (4 GPU):
    wave 0: rank 0,1 各处理 batch/2 的 requests
    每个 rank 内部用 EP=2: expert 0,1 在 rank 0; expert 2,3 在 rank 1
  ```
- 通信开销对比: DP sync O(1) per wave vs EP all-to-all O(k·hidden_dim·seqlen) per MoE layer

为什么：C082 EP 做 expert 维度切分（同一 batch 的不同 experts 在不同 GPU），C101 DP 做 batch 维度切分（不同 batch 在不同 GPU）。DP + EP 组合是 DeepSeek-V3 多节点部署的核心模式。理解 wave/batch coordination 是看懂 vLLM `DPEngineCoreProc` 的前提。

验证：DP=2 + EP=2 运行 OPT-125m + MoE，与单 GPU MoE 输出一致。

```python
from dataclasses import dataclass

        """

```

```
                                #   producer: mark block PENDING → start_transfer()
```

能力：
- 跨进程 block 传输: serialize K,V → shared memory / NCCL send → deserialize → write
- Sequence number 一致性: per-block seq_num 保证 consumer 不写 stale data
- 与 EP 集成: EP all-to-all 选 expert GPU 后，connector 迁移已有 KV cache
- 与 PP 集成: PP stage 切换时，connector 迁移完整 KV blocks（而非逐 token send/recv）

为什么：C084 PP 用 send/recv activation（逐 token，1F1B pipeline），但 KV Connector 是不同的通信抽象——不是 activation forwarding，而是完整的 KV block 生命周期迁移。这在以下场景中很重要：
- EP 切换 expert placement 时：已有 KV cache 需要迁移到新的 expert GPU
- KV cache 预热：从其他 engine instance 导入预计算的 KV cache
- Async scheduling (C053)：scheduler 决定让 request 在另一 worker 上继续时

验证：两个独立 Worker 进程，connector 传输一个 block，consumer 正确恢复 K,V tensors。

```
         | DP (batch)          | EP (expert)               | TP (weight)
```

```markdown
# Custom All-Reduce 分析

## NCCL All-Reduce 的 Overhead

TP=8 通信开销:
- 每层 Linear: 3 次 all-reduce (QKV + output + MLP)
- 32 层 × 3 次 = 96 次 all-reduce per token
- 单次 NCCL all-reduce 延迟: ~10μs (ring algorithm, intra-node)
- 总计: 96 × 10μs = ~1ms all-reduce overhead per token

TP=2 通信开销:
- 单次 NCCL all-reduce: ~5μs (只有 2 GPU，直接 point-to-point)
- 总计: ~0.5ms per token
- 结论: TP=2 不需要 custom all-reduce

## Custom All-Reduce 策略

vLLM custom_all_reduce.py 的核心优化:
1. Shared memory: GPU0↔GPU1 用 shared memory (NVLink 直连)
2. Kernel fusion: all-reduce + activation 在同一个 CUDA stream
3. Ring algorithm: GPU0→GPU1→...→GPU7→GPU0 (intra-node only)

带宽对比 (TP=8, hidden_dim=4096):
  NCCL ring: 150 GB/s → 27μs per all-reduce
  Custom (shared memory + NVLink): 300 GB/s → 14μs per all-reduce

## 为什么不总是用 Custom

- TP=2: 只有 2 GPU，所有数据都走 NVLink，没有拓扑选择问题
- TP=8, multi-node: 跨 node 通信必须用 NCCL (custom 只支持 intra-node)
- 维护成本: custom kernel 与 CUDA 版本和 GPU 型号强绑定
```

分析内容：
```markdown
# Chunked Prefill + Paged Decode 分析

## 为什么需要 Chunked Prefill

问题: 一个长 prompt (32K tokens) 会"饿死"所有 decode requests。

Naive 方案:
  step 1: prefill 32K tokens (耗时 200ms)
    所有 decode requests 等 200ms → TTFT 爆炸

Chunked prefill:
  step 1: prefill chunk 1 (4K tokens, 耗时 25ms)
          + decode batch (耗时 5ms)
  step 2: prefill chunk 2 (4K tokens, 耗时 25ms)
          + decode batch (耗时 5ms)
  ...
  step 8: prefill chunk 8 (final) + decode batch
  → 每个 step 耗时 ~30ms, decode TTFT 不爆炸

## Chunked Prefill 的 KV Cache 管理

每个 prefill chunk 需要新的 KV cache block:
  chunk 1: allocate blocks[0:4]
  chunk 2: allocate blocks[4:8]
  ...
  每个 chunk 的 block 追加到 request 的 block table

## Paged Decode 的 Slot Mapping

Paged decode 和 prefill 的 slot_mapping 不同:
  Prefill: slot_mapping = contiguous (新写入)
  Decode: slot_mapping = scattered (追加 1 token 到已有 block)

build_slot_mappings():
  对 prefill tokens → 新的 contiguous slots
  对 decode tokens → 追加到当前 block 的最后一个位置

## vLLM 实现要点

- Chunked prefill batch size: max_num_batched_tokens / num_chunks
- Scheduler chunk budget: 每个 step 用多少 token 做 prefill
- 与 CUDA Graph 兼容: decode batch 可以用 CUDA Graph，prefill 不行
```

```markdown
# 量化方法全景对比

| 方法     | 精度    | Weight 格式       | Activation 量化   | Kernel 实现      | 适用场景               |
|----------|---------|-------------------|-------------------|------------------|------------------------|
| FP8 E4M3 | 8-bit   | per-channel scale | dynamic           | torch.float8     | H100/B200 推理          |
| AWQ      | 4-bit   | group pack (32×32)| FP16 (不量化)     | custom CUDA      | 通用推理，精度损失小      |
| GPTQ     | 4-bit   | column pack       | FP16 (不量化)     | custom CUDA      | 需要 per-column 校准     |
| Marlin   | 4-bit   | 32×32 tile pack   | FP16 (不量化)     | custom CUDA (快速)| AWQ/GPTQ 的通用 fast kernel |
| NVFP4    | 4-bit   | block-wise        | block-wise        | CUTLASS/Hopper   | B200 原生 FP4 tensor core|

1. Weight packing format:
   - AWQ: group_size=128, per-group scale+zero
   - GPTQ: order='column', bit-packed int32
   - Marlin: 32×32 tile layout, GPU-specialized

2. Activation handling:
   - FP8: dynamic per-token quantization
   - AWQ/GPTQ/Marlin: FP16 activation (只量化 weight)
   - NVFP4: block-wise dynamic (weight + activation both in FP4)

3. Dequantization path:
   - AWQ: unpack → scale → FP16 → matmul
   - Marlin: fused unpack + scale + matmul (single kernel)
   - NVFP4: hardware dequant via Hopper tensor core

## 为什么量化是面试高频

- FP8 是 H100 的 "sweet spot": 精度损失小, 硬件 native 支持
- AWQ vs GPTQ 的哲学差异: activation-aware (AWQ) vs 最优 inverse Hessian (GPTQ)
- Marlin 是工程奇迹: 一个 kernel 同时支持 AWQ 和 GPTQ 两种 weight format
```

```markdown
EP 的痛点:

- 用户量增长 → 需要 4 GPU (EP=4)
```

```markdown
## Training → Inference 的权重同步

RLHF / GRPO 训练流程:
  1. Training loop: 更新模型权重
  2. Sync weights: training engine → inference engines (TP×PP workers)
```
