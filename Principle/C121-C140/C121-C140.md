## C123 — MLA fused decompress kernel

新增：
```
triton_kernels/

                               #   1. kv_lora (compressed) [seq, kv_lora_rank]
                               #   2. decompress K: kv_lora @ W_UK  →  [seq, num_heads, head_dim]
                               #      (或 fused: K = kv_absorbed_proj(input))

## C124 — Ring Attention 内层 kernel

目标：实现 CP (Context Parallel) 的核心——ring_step: 本地 QK^T + send K,V tile → 远端 QK^T + LSE online merge。

新增：
```
triton_kernels/
  ring_attention_step.py      # @triton.jit ring_step_kernel:
                               #   给定: Q_local, K_current, V_current, LSE_prev, O_prev
                               #   1. S = Q_local @ K_current^T × sm_scale
                               #   2. m_new = max(LSE_prev.m, rowmax(S))
                               #   3. P = exp(S - m_new)
                               #   4. l_new = exp(LSE_prev.m - m_new) × LSE_prev.l + rowsum(P)
                               #   5. O_new = diag(exp(LSE_prev.m - m_new)) @ O_prev + P @ V_current
                               #   6. update LSE = (m_new, l_new)
```

验证：
- CP=2: seqlen=4096 split 到 2 GPU → 2 ring steps → 与单 GPU full attention 数值一致
- 每 step latency breakdown: compute (QK^T+PV) vs communication (send/recv K,V tile)

为什么：
- Ring Attention 是长序列推理的基石 (128K+ tokens)
- 核心难点是 online softmax 跨 GPU 的正确性——LSE merge 公式的推导和执行
- 面试: "CP=4, 序列 128K。解释每一步 ring step 的通信量和计算量"

  topk_gating_fused.py        # @triton.jit:
                               #   per token:
                               #     1. load router_logits [num_experts] → SRAM
                               #     2. topk selection (bitonic sort in SRAM):
                               #        选出 top-2 logits + indices
                               #     3. softmax(top-2):
                               #        weights = softmax(selected_logits)
                               #     4. store: weights + indices → output
```

验证：
- 8 experts, top_k=2: fused topk vs PyTorch topk + softmax → latency + 数值一致
- Bitonic sort performance vs torch.topk for small k (k=2,3,4)

为什么：
- Router 是每个 token 的必经路径——不能有 kernel launch overhead
- 理解 bitonic sort 是 SRAM-friendly 的排序算法——比 heap sort 更 GPU-efficient
- 面试: "在 GPU 上做 top-k，为什么不用 heap sort？"

                               #   ]
                               #   @triton.autotune(configs, key=['M', 'N', 'K'])

                               #   def gemm_kernel(...): ...

验证：
- GEMM (M=4096, N=4096, K=4096): 5 best configs → latency(μs) + theoretical FLOP/s vs achieved

- 编译器不知道 GPU-specific 的最优 tile size——需要运行时搜索
