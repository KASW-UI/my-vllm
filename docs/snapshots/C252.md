# C252 — KV 事件总线

## Goal

Closes the A-level "KV 事件总线" gap from
`phase3-distributed-runtime-plan.md`.  Phase 4 v2 progress: 3/10
commits closed.

## New Features

### 1. `my_vllm/distributed/kv_events.py` (NEW, ~470 lines)

Mirrors `vllm/distributed/kv_events.py` (543 lines).  Scope reductions:

* `msgspec.Struct` base — replaced with `@dataclass` (msgspec not vendored).
* `ExternalBlockHash` — replaced with plain `int` (the hash values are computed by the scheduler; my-vllm uses whatever algorithm the scheduler produces).
* `ZmqEventPublisher` — **omitted** (ZMQ not vendored; the C242 SHM broadcast primitive is the substitute).
* `KVEventsConfig` — minimal Pydantic-free dataclass (config is duck-typed).
* Wire-format: kept compatible with vLLM's JSON layout (events are `asdict()`-serializable so consumers across processes can reconstruct them via msgpack / JSON).

**Event types** (mirrors vLLM):
* `KVCacheEvent` — base class.
* `BlockStored` — block hashes + token IDs + medium + cache-spec metadata.
* `BlockRemoved` — block hashes + medium.
* `AllBlocksCleared` — clear-all signal.

**Aggregation**:
* `KVEventAggregator` — multi-worker dedup (counters; `get_common_events()` returns only events emitted by all workers).
* `KVEventBatch` — ts + events + data_parallel_rank.

**Publisher surface**:
* `EventPublisher` ABC.
* `NullEventPublisher` — no-op default.
* `InMemoryEventPublisher` — in-process pub/sub with replay buffer (substitutes for `ZmqEventPublisher`).
* `EventPublisherFactory` — registry + factory.

**Connector helper**:
* `KVConnectorKVEvents` — dataclass-style event collector (replaces vLLM's ABC; the production use case is "connector stores events → scheduler drains them").

### 2. `my_vllm/distributed/stateless_coordinator.py` (NEW, ~280 lines)

Mirrors `vllm/distributed/stateless_coordinator.py` (381 lines).  Scope reductions:

* **No TCPStore / stateless process group** — vLLM's `StatelessGroupCoordinator` is a 3-port multi-process group built on `torch.distributed.TCPStore` + `StatelessProcessGroup`.  my-vllm doesn't vendor either; the C243 weight transfer path uses vanilla `torch.distributed.broadcast` directly, and the C242 SHM broadcast primitive handles same-host messages.
* **No `StatelessProcessGroup`** — replaced with an in-process `threading.RLock` + Python queue for producer → consumer event routing.
* **No `GroupCoordinator`** — replaced with a much simpler `StatelessCoordinator` that just routes events between registered producers and consumers in one process.

**Core API**:
* `register_producer(engine_id, callback, medium, locality)` — register a producer engine with a callback that emits events.
* `register_consumer(engine_id, callback, block_filter)` — register a consumer with an optional `set[int]` block filter.
* `publish(events, producer_engine_id=None)` — route events to all consumers (applying filters).
* `publish_event(event, producer_engine_id=None, ts=None)` — convenience for single events.
* `trigger_kv_transfer(consumer_engine_id, block_hash, source_engine_id)` — record a transfer trigger for a consumer.
* `get_kv_transfer_triggers(consumer_engine_id=None)` — retrieve recorded triggers.
* `get_event_log() / get_events_for_producer() / get_events_for_block_hash()` — event log inspection.

**Singleton**:
* `get_stateless_coordinator()` — module-level singleton (mirrors vLLM's pattern).
* `reset_stateless_coordinator()` — test helper.

### 4. C251 `take_events` integration

The C251 `take_events` hook returns a list of `KVCacheEvent`s.  The
C252 coordinator's `collect_connector_events(events)` helper consumes
this list and routes the events to registered consumers:

```python
# In the scheduler (every step):
connector_events = connector.take_events()  # C251
coordinator.collect_connector_events(connector_events)  # C252
```

## Runtime Flow

```
Producer (Prefill Completes)
    │
    ├── kv_events.InMemoryEventPublisher.publish(KVEventBatch(
    │       ts=now,
    │       events=[BlockStored(block_hashes=[...], token_ids=[...])]
    │   ))
    │
    └── coordinator.publish(batch, producer_engine_id="engine-0")
            │
            ├── Validate producer is registered (or log debug)
            ├── Store event in _event_log (FIFO bounded buffer)
            └── For each registered consumer:
                  ├── If block_filter is set: skip non-matching
                  ├── If consumer.enabled is False: skip
                  └── consumer.callback(event)
                          │
                          └── (consumer logic)
                                │
                                ├── if event is BlockStored:
                                │     for hash in event.block_hashes:
                                │       if hash in consumer.block_filter:
                                │         coordinator.trigger_kv_transfer(
                                │           consumer_id, hash, source_engine_id)
                                │
                                └── if appropriate: KV transfer via NIXL
                                      (consumer calls get_num_new_matched_tokens
                                       which returns the matched token count)
```

## Current Capability

* **Full event types** — BlockStored / BlockRemoved / AllBlocksCleared
  with hash + equality semantics.
* **In-process publisher** — `InMemoryEventPublisher` with subscriber
  callbacks + auto-assigned data_parallel_rank + bounded replay buffer.
* **Multi-worker dedup** — `KVEventAggregator` deduplicates events
  emitted by all TP ranks.
* **Coordinator routing** — producer registration + consumer
  subscription + per-consumer block filter + event log + KV transfer
  trigger API.
* **Singleton** — process-wide coordinator accessible via
  `get_stateless_coordinator()`.
* **C251 take_events integration** — `collect_connector_events()`
  helper bridges the connector's event list to the coordinator.

## Current Limitation

1. **In-process only** — cross-process routing requires either the
   C242 SHM broadcast primitive (same-host) or a TCP-based event bus
   (deferred to a later C25x commit).
2. **No background publisher thread blocking** — `InMemoryEventPublisher`
   spawns a daemon thread for delivery; the thread is not joined on
   `shutdown()` (relies on `SHUTDOWN_TIMEOUT` polling).
3. **No ZmqEventPublisher** — cross-node event delivery requires either
   a TCP-based publisher or the C242 SHM broadcast primitive (both
   deferred).
4. **No KV transfer logic** — the coordinator records triggers but
   does not actually issue NIXL READ transfers.  The consumer's
   `get_num_new_matched_tokens` callback is the integration point.
5. **No replay SKIP** — the InMemoryEventPublisher's replay buffer
   is internal-only; there's no client-facing "replay from seq N"
   API yet (the vLLM ZMQ equivalent exposes this for late-joining
   subscribers).
6. **No serialization optimization** — JSON encoding is used for the
   replay buffer (slow / large).  Production would use msgpack.
