# C255 — KV Offload base + config

## Goal

Closes the A-level "KV Offload base + config" gap from
`phase3-distributed-runtime-plan.md`.  Phase 4 v2 progress: 6/10
commits closed.

This is the **plug-in surface** for KV cache offloading backends
— the abstract interfaces + config + factory + file-layout
primitive that future C256 (CPU/NVMe tiering) and C257 (Simple
KV Offload) implementations slot into.  No concrete backend
ships in C255.

## New Features

### 1. `my_vllm/v1/kv_offload/` package (NEW)

Four modules + facade:

* **`base.py`** (~530 lines, extracted from
  `vllm/v1/kv_offload/base.py` subset):
  - `OffloadKey = NewType("OffloadKey", bytes)` +
    `make_offload_key(block_hash, group_idx)` /
    `get_offload_block_hash` / `get_offload_group_idx`.
    Encoding: `<block_hash><group_idx_be_u32>`.
  - Enums: `LookupResult` (MISS / HIT / HIT_PENDING / RETRY),
    `OffloadPolicy` (BLOCK_LEVEL / REQUEST_LEVEL),
    `Locality` (LOCAL / REMOTE).
  - Dataclasses: `ReqContext`, `RequestOffloadingContext`,
    `ScheduleEndContext`, `PrepareStoreOutput`, `OffloadingEvent`,
    `CanonicalKVCacheTensor` / `CanonicalKVCacheRef` /
    `CanonicalKVCaches`, `TransferResult`.
  - `LoadStoreSpec` ABC + `BlockIDsLoadStoreSpec` ABC +
    `GPULoadStoreSpec` (concrete; asserts
    `sum(group_sizes) == len(block_ids)` and
    `len(block_indices) == len(group_sizes)`).
  - Metric metadata: `OffloadingMetricMetadata` +
    `OffloadingCounterMetadata` /
    `OffloadingGaugeMetadata` /
    `OffloadingHistogramMetadata` (with `buckets`).
  - `OffloadingKVEventsConfig` (event-publishing config).
  - **`OffloadingManager` (ABC)** — scheduler-side:
    `lookup` / `prepare_load` / `touch` / `complete_load` /
    `prepare_store` / `complete_store` / `on_new_request` /
    `on_request_finished` / `take_events` /
    `on_schedule_end` / `has_pending_work` /
    `reset_cache` / `get_stats` / `shutdown`.
    The first 4 are abstract; the rest are default no-ops.
  - **`OffloadingWorker` (ABC)** — worker-side:
    `submit_store` / `submit_load` /
    `get_finished` / `wait` (all abstract) +
    `shutdown` (default no-op).
  - **`OffloadingSpec` (ABC)** — connector spec:
    `get_manager()` + `get_worker(kv_caches)` (both abstract).
    Constructor reads `extra_config` for `self_describing_kv_events`
    + `offload_prompt_only` flags; aggregates
    `tokens_per_block` from groups; sets `tokens_per_hash` /
    `blocks_per_chunk` from cache config. `build_metric_definitions`
    returns empty dict by default.
* **`config.py`** (~70 lines): frozen dataclasses
  `OffloadingGroupConfig` / `OffloadingModelConfig` /
  `OffloadingCacheConfig` / `OffloadingParallelConfig` /
  `OffloadingConfig` (aggregation).
* **`factory.py`** (~70 lines):
  `OffloadingSpecFactory` — lazy-loading registry with
  `register_spec` / `get_spec_cls` / `create_spec` / `reset` /
  `known_specs`. Ad-hoc specs fall back to
  `extra_config["spec_module_path"]` + `importlib.import_module`.
* **`file_mapper.py`** (~140 lines):
  `FileMapper` — disk layout primitive. `get_file_name(key)`
  produces `<base>_r<rank>/<hhh>/<hh>_g<group_idx>/<hash>.bin`.
  `get_config_file_path()` returns `<base>/config.json`.
  `parallel_agnostic=True` (with `config.parallel
  .is_parallelism_agnostic=True`) collapses TP/PP/PCP/DCP to 1
  and rank to 0 so different parallelism layouts of the same
  model share a base path.
  `base_path = <root_dir>/<safe_model_name>_<sha256-prefix>` —
  HF IDs have `/` → `_`.
* **`__init__.py`** (facade): re-exports the public surface for
  `from my_vllm.v1.kv_offload import OffloadingManager, ...`.

## Runtime Flow

The plug-in surface only — concrete backends land with C256/C257:

```
                    VllmConfig
                         │
                         ▼
                 OffloadingConfig  (frozen, from config.py)
                         │
                         ▼
            OffloadingSpecFactory.get_spec_cls(extra_config)
                         │     │
                         │     └─→ register_spec (pre-registered,
                         │         lazy import via importlib)
                         │     └─→ spec_module_path (ad-hoc)
                         ▼
                 OffloadingSpec (ABC)
                  │             │
                  ▼             ▼
       OffloadingManager   OffloadingWorker
       (scheduler-side)    (worker-side, after GPU init)
            │                     │
            │                     ▼
            │              async KV transfers
            │              (submit_store / submit_load)
            ▼                     │
       lookup / prepare_load /    ▼
       prepare_store /      get_finished() drain
       take_events /
       on_schedule_end /
       has_pending_work
```

The disk-tier path uses `FileMapper` to translate `OffloadKey`s
into on-disk paths so different workers (different rank) write
into per-rank subfolders, and different layouts (different
TP/PP) land in different base paths (unless
`is_parallelism_agnostic=True`).

## Current Capability

* Pluggable `OffloadingSpec` interface with lazy-loading factory.
* `OffloadingManager` ABC (scheduler-side) covers the full
  vLLM V1 surface — lookup, prepare/load/store, on_new_request,
  on_request_finished, take_events, on_schedule_end,
  has_pending_work, reset_cache, get_stats, shutdown.
* `OffloadingWorker` ABC (worker-side) covers submit_store,
  submit_load, get_finished, wait, shutdown.
* `LoadStoreSpec` hierarchy — base + `BlockIDsLoadStoreSpec`
  (numpy int64 block IDs) + `GPULoadStoreSpec` (multi-group
  support with group_sizes + block_indices).
* Canonical KV cache representation (per-tensor /
  per-layer-ref / per-group) for offload workers that need
  the raw GPU tensors (used by C256/C257).
* `OffloadingConfig` (frozen) with group / model / cache /
  parallel sub-configs — production wiring lands with C256.
* `OffloadingSpecFactory` lazy registry + ad-hoc
  `spec_module_path` fallback. Duplicate registration is a
  hard error.
* `FileMapper` disk layout — parallelism-agnostic collapse,
  HF model-name safety, deterministic SHA-256 digest.
* 72 new test cases cover all of the above.
* Legacy C134 / C143 / C212 / C250-C254 tests still pass
  (888 passed, was 816; +72 C255 cases).  2 pre-existing
  C212 attention-match failures carry over (cosine NaN —
  unrelated).

## Current Limitation

* **No concrete backend ships in C255.**  CPU / NVMe /
  tiering implementations land with C256 (KV Offload tiering)
  + C257 (Simple KV Offload).
* `OffloadingConfig` is constructed directly in C255 tests;
  production wiring (extracting these fields from a real
  `VllmConfig`) lands with C256.
* `FileMapper` is exercised but not consumed (no disk-tier
  spec yet).
* ABCs (`OffloadingManager` / `OffloadingWorker` /
  `OffloadingSpec`) are not subclassed by any concrete code
  yet — the test suite uses local `_Dummy*` helpers.
