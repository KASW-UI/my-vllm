## What C146 did

### 1. `lora_model.py` (new)

Mirrors vLLM V1 lora/lora_model.py:LoRAModel.

- **`LoRAModel`** — runtime wrapper holding the base model's
  `nn.Module` + a `lora_modules: dict[str, BaseLayer]`
  (base_module_name → LoRA-augmented wrapper). Public API:
  `register_module`, `add_lora`, `remove_lora`, `set_lora`,
  `get_lora`, `list_loras`, `active_lora_int_id` property.

### 2. `model_manager.py` (new)

Mirrors vLLM V1 lora/model_manager.py:LoRAModelManager.

- **`LoRAModelManager`** — `add_lora` / `remove_lora` register /
  unregister adapters with the model; `load_adapter(path)` is
  a stub that acknowledges the path but does no HF PEFT
  weight-mapping (out of scope per §8); `activate_adapter(id)`
  marks the adapter active.

### 3. `worker_manager.py` (new)

Mirrors vLLM V1 lora/worker_manager.py:LoRAWorkerManager.

- **`LoRAWorkerManager`** — single-process default;
  `add_lora` / `remove_lora` / `set_lora` / `load_adapter` /
  `list_adapters` delegate to the local `LoRAModelManager`.
  Multi-worker broadcast is a no-op stub.

### 4. `v1/worker/lora_model_runner_mixin.py` (new)

Mirrors vLLM V1 v1/worker/lora_model_runner_mixin.py:
LoRAModelRunnerMixin.

- **`LoRAModelRunnerMixin`** — mix into `GPUModelRunner`.
  `init_lora(model, max_loras, max_lora_rank, device)` wires up
  `LoRAModel` + `LoRAModelManager` + `LoRAWorkerManager`;
  `update_lora_modules()` is a stub (real impl walks
  `model.named_modules()` and replaces Linear / ColumnParallel /
  RowParallel with the corresponding LoRA subclass); the
  `add_lora` / `remove_lora` / `set_lora` / `list_loras` hooks
  delegate to the worker_manager.

## Current Limitation

- **`load_adapter` is a stub** — no HF PEFT weight mapping.
  Real impl requires `peft` library + checkpoint parsing
  (out of scope per §8).
- **`update_lora_modules` is a stub** — the runner mixin's
  `update_lora_modules` is a no-op. Real impl walks
  `model.named_modules()` and replaces Linear / ColumnParallel
  Linear with the LoRA wrappers; requires `OPTForCausalLM`'s
  weight-mapping to be LoRA-aware.
- **No per-request adapter dispatch** — the runner mixin
  doesn't yet consult `request.lora_request` during
  `execute_model` to swap the active adapter per request.
- **`OPTForCausalLM` still uses `nn.Linear` directly** — the
  LoRA layers are dormant until `update_lora_modules` is wired.
- **`FusedMoEWithLoRA` is a skeleton** (no per-expert routing).
- **No Triton SGMV/BGMV kernels** — the dense path uses pure
  torch.
