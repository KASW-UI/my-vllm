# C247 — EP 弹性 rebalance 闭环

> Closes the A-level "EP 弹性 rebalance 闭环 (接 C230)" gap from
> `phase3-distributed-runtime-plan.md` § Phase 3.
>
> Wires real `progress()` callbacks to the state machine:
> - **TCP barrier** hook on every transition (default: no-op logger;
>   production wires `torch.distributed.TCPStore`).
> - **NCCL weight transfer** hook via `NCCLWeightTransferEngine`
>   (C243) on TRANSFER_EXPERT_MAPPING + TRANSFER_WEIGHTS transitions
>   during scale-up.
>
> The state machine becomes the *plumbing* that bridges pure policy
> decisions (C230 `decide_and_create`) to real side effects (TCPStore
> barriers + NCCL broadcasts).

## Goal

Reproduce vLLM's elastic EP rebalance state machine end-to-end with
callback-based hook wiring, so:

1. **Real progress()** — each state transition fires the
   protocol's expected barrier + transfer hooks.
2. **TCP barrier hook** — `barrier_fn(name, participants)` is
   invoked before each transition; default is a no-op logger,
   production wires `torch.distributed.TCPStore`.
3. **NCCL weight transfer hook** — `weight_transfer_fn(src, dst,
   kind)` is invoked for TRANSFER_EXPERT_MAPPING +
   TRANSFER_WEIGHTS transitions; production wires
   `NCCLWeightTransferEngine` (C243) broadcast + receive_weights.
4. **run_to_completion() helper** — drives the state machine
   end-to-end with a max_steps guard.
5. **End-to-end policy → state machine** — `decide_and_create`
   (C230) returns a fresh state machine, `run_to_completion()`
   drives it to COMPLETE.

## State Machine Architecture

```
┌─────────────────────────────────────────────────────────────────────────┐
│  decide_and_create(vllm_cfg, signal, policy)                            │
│    ↓ policy.decide(signal) → EPRebalanceDecision                        │
│    ↓ create_scaling_state_for_decision(...) → ElasticEPScalingState    │
└─────────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────────┐
│  ElasticEPScalingState (per-event instance)                              │
│    progresses state machine via progress() / run_to_completion()         │
│                                                                         │
│    Per transition, _advance(next_state, barrier_name?, weight_transfer?) │
│      fires: 1. barrier_fn(name, participants) BEFORE state change       │
│             2. weight_transfer_fn(src, dst, kind) BEFORE state change     │
│             3. records transition + barrier / transfer in event logs    │
│                                                                         │
│    For scale_up existing (the heavy path):                               │
│      WAIT_NEW_CORE_INIT → CREATE_STANDBY → TRANSFER_EXPERT_MAPPING     │
│        ↓ barrier + weight_transfer(expert_mapping)                      │
│      WAIT_NEW_CORE_WEIGHTS_INIT → TRANSFER_WEIGHTS                      │
│        ↓ barrier + weight_transfer(weights)                             │
│      SYNC_KV_MEMORY_SIZE → SWITCH_AND_PREPARE → EPLB_RESHUFFLE          │
│        ↓ barrier on each                                                │
│      COMPLETE                                                            │
└─────────────────────────────────────────────────────────────────────────┘
```

Production wiring:
- `barrier_fn` → `torch.distributed.TCPStore(...).barrier()` keyed
  by `barrier_name`, with participants listed in the store's
  per-key prefix.
- `weight_transfer_fn` → when `kind == "weights"`, calls
  `NCCLWeightTransferEngine.trainer_send_weights(...)` on rank 0 and
  `engine.receive_weights(...)` on each new rank (C243 multi-process
  round-trip).  When `kind == "expert_mapping"`, sends the
  MoE-expert→rank assignment table via the same engine's packed
  broadcast.

## Current Capability

* **Real progress() wiring** — `progress()` returns True after
  firing the callback hooks for the transition; idempotent after
  COMPLETE.
* **run_to_completion() helper** — drives the state machine to
  COMPLETE with a max_steps guard (default 64).
* **Event logs** — `state.transitions` (list of (from, to, scale_type)),
  `state.barriers` (list of (name, scale_type)),
  `state.weight_transfers` (list of (src, dst, kind)) for inspection.
* **TCP barrier hook signature** — `barrier_fn(barrier_name,
  participants)`.  Default no-op.
* **NCCL weight transfer hook signature** — `weight_transfer_fn
  (src_worker_id, dst_worker_id, kind)`.  Default no-op.
* **End-to-end** — `decide_and_create` (C230) → `run_to_completion`
  (C247) drives a full policy-driven scale-up + scale-down sequence.
* **30 tests** across 10 classes covering all 4 (scale_type,
  worker_type) state paths + edge cases.

## Current Limitation

* **No real TCPStore wired** — the barrier callback is a no-op
  logger; production wire-up to `torch.distributed.TCPStore` is
  deferred to the engine controller layer.
* **No real NCCL broadcast wired** — the weight_transfer callback
  is a no-op logger; production wire-up to
  `NCCLWeightTransferEngine.trainer_send_weights` + `receive_weights`
  (C243) is deferred.
* **No EPLB reshuffle action** — the EPLB_RESHUFFLE transition
  emits a barrier but doesn't actually redistribute experts.  EPLB
  is out of scope for my-vllm (no MoE model vendored).
* **No "new" + "removing" engines managed locally** — the state
  machine drives the "existing" / "remaining" side only; the SPAWN /
  SHUTDOWN of the new / removing engines is orchestrated by the
  engine frontend (out of scope).
