# C118: Triton slot_mapping kernel — unified batch metadata

## Goal

Replace the per-req / per-token Python loop in `BlockTables.compute_slot_mappings` with a single Triton kernel. Aligns with `vllm/vllm/v1/worker/gpu/block_table.py:_compute_slot_mappings_kernel` (single KV cache group, no CP, no padding).

## New Features

### `v1/attention/ops/triton_slot_mapping.py` (new)

```python
@triton.jit
def _slot_mapping_kernel(
    query_start_loc_ptr,   # [num_reqs + 1] int32
    positions_ptr,          # [num_tokens] int64
    block_table_ptr,        # [num_reqs, max_blocks] int32
    block_table_stride,
    slot_mapping_ptr,       # [num_tokens] int64 (out)
    BLOCK_SIZE: tl.constexpr,
):
    batch_idx = tl.program_id(0)
    start = tl.load(query_start_loc_ptr + batch_idx)
    end   = tl.load(query_start_loc_ptr + batch_idx + 1)
    row_base = block_table_ptr + batch_idx * block_table_stride
    for i in range(start, end):
        pos = tl.load(positions_ptr + i).to(tl.int64)
        block_idx = pos // BLOCK_SIZE
        offset    = pos % BLOCK_SIZE
        block_id  = tl.load(row_base + block_idx)
        slot_id   = block_id * BLOCK_SIZE + offset
        tl.store(slot_mapping_ptr + i, slot_id)
```

One program per request; iterates that request's tokens in `range(start, end)`. Single batched kernel launch replaces the prior Python double-loop with `.item()` syncs.

### `BlockTables.compute_slot_mappings`

Now delegates to `compute_slot_mapping(...)` from the new module. Same public signature, same return value (`self.slot_mappings[:num_tokens]`).

## Runtime Flow

```
GPUModelRunner._prepare_inputs(scheduler_output)
  ├─ for d in new_datas:                 # build flat input_ids, positions, ...
  ├─ for rid in cached_reqs:
  └─ self.block_tables.compute_slot_mappings(
         query_start_loc, positions, num_tokens)
        └─ triton_slot_mapping.compute_slot_mapping(...)
              └─ _slot_mapping_kernel[(num_reqs,)](...)   # single launch
```

Before this change the same method ran a Python `for req_idx in range(num_reqs):` loop with `query_start_loc[req_idx].item()` and `positions[tok_idx].item()` per token — a CPU sync per token.

## Current Capability

- `python run.py`: identical 50-token output to C117. The Triton kernel computes the same `slot_id = block_id * block_size + offset` math as the prior Python loop.
- 191 passed / 55 failed — same baseline as C117. The two new failures (test_compute_slot_mappings_*) were fixed by gating on `torch.cuda.is_available()`.
- The hot path is now `.item()`-free in `_prepare_inputs` for the slot_mapping write path.

## Current Limitation

- `compute_slot_mapping` writes the first `num_tokens` entries; vLLM's kernel also pads the remaining `max_num_tokens` to `PAD_SLOT_ID` for CUDA-graph capture. C119 (CUDA graph) will re-introduce the padding path.
- No CP (context-parallel) branch — single-rank, no interleave. Mirrors my-vllm's scope (TP=1, PP=1).
- The Triton kernel iterates tokens in a Python-style `for i in range(start, end):` inside one program; for large query chunks (>64 tokens per req), a `tl.range(start, end, TRITON_BLOCK_SIZE)` with masked vectorized loads/stores would be faster. Acceptable for OPT-125m prompts (<128 tokens).
- Block-table gather (`gather_block_tables` in vLLM) is not implemented — the runner reads `self.block_tables.block_table` directly via slicing.
