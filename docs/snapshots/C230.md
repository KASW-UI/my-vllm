# C230: Elastic EP — rebalance dispatch + ParallelConfig.data_parallel_size

## Goal

Wire up the **control plane** of elastic expert parallelism
(scaling): the policy that decides when to scale the data-parallel
group, plus a factory that bridges the policy's decision to the
existing `ElasticEPScalingState` state machine.

`ElasticEPScalingState` (the multi-phase scale-up / scale-down
state machine) was already implemented as a skeleton under C110
(four `IntEnum` state sequences + a `progress()` walker).  C230
closes the B2-b "保留 + 接线" path from `docs/cleanup-plan.md`
§3: keep the state machine, add the rebalance path, document
the integration points.

Covers JD **加分 #6 「弹性计算」** — establishes when-to-scale
decisions on top of the architecture-aligned state machine (the
"how").  Engine-side wiring (TCP-store barriers, NCCL weight
transfers, EPLB reshuffle, KV cache memory sync) lives in the
state machine; for our JD-aligned subset we keep the decision
path self-contained and tested.

## What's in this commit

### 1. `my_vllm/distributed/elastic_ep/rebalance.py` (NEW)

Mirror vLLM's control plane — the "when" to scale decision,
separated from the "how" (state machine).  Three main pieces:

#### 1a. Signal / Decision dataclasses

```python
@dataclass
class EPRebalanceSignal:
    current_dp_size: int
    target_dp_size: int | None = None
    kv_cache_utilization: float = 0.0
    pending_prefill_tokens: int = 0
    num_active_requests: int = 0
    elapsed_seconds: float = 0.0

@dataclass
class EPRebalanceDecision:
    scale_type: Literal["scale_up", "scale_down", "hold"]
    new_dp_size: int
    reason: str = ""
    metadata: dict = field(default_factory=dict)
```

The signal bundle is what an engine-core would gather from the
scheduler periodically (see vLLM
`vllm/v1/engine/core_client.py:gather_rebalance_signal`).

#### 1b. `EPRebalancePolicy` ABC + two concrete policies

```python
class NoOpEPRebalancePolicy(EPRebalancePolicy):
    """Always returns 'hold' — default for static deployments."""

class ThresholdEPLoadPolicy(EPRebalancePolicy):
    """Threshold-driven scale-up / scale-down on KV cache utilization.

    Decision order:
      1. Explicit user target → honor it (capped to [min,max] bounds).
      2. Cold-start hysteresis (min_downtime_seconds) → hold.
      3. util ≥ up_threshold  and not at max → scale_up by 1.
      4. util ≤ down_threshold and not at min → scale_down by 1.
      5. otherwise → hold.
    """
```

The `ThresholdEPLoadPolicy` is intentionally simple: production
vLLM uses more sophisticated signals (expert-load variance, queue
depth, traffic shaping…).  Plug in a custom subclass to override.

#### 1c. Factory + convenience

```python
def create_scaling_state_for_decision(
    vllm_config, decision
) -> ElasticEPScalingState | None:
    """Bridge policy → state machine.

    * 'hold' → None.
    * target_dp_size == current_dp_size → None (skip redundant work).
    * 'scale_up'   → ElasticEPScalingState(worker_type='existing').
    * 'scale_down' → ElasticEPScalingState(worker_type='remaining').
    """

def decide_and_create(
    vllm_config, signal, policy=None
) -> ElasticEPScalingState | None:
    """End-to-end convenience.  Uses ThresholdEPLoadPolicy by default."""
```

Worker type semantics:

  * **Scale-up** controlling engine is "existing" (the survivors
    drive the state machine; new engines live on the OTHER side
    of the same scaling event).
  * **Scale-down** controlling engine is "remaining" (same logic).

The "new" / "removing" workers are managed by separate engine
cores — that orchestration lives at the engine-frontend layer
(see vLLM `vllm/v1/engine/core_client.py`).  For our JD-aligned
subset we keep the state machine self-contained on the
controlling side.

### 2. `my_vllm/distributed/elastic_ep/elastic_state.py` — fix `progress()`

The skeleton had an inverted `progress()` semantic:

```python
# OLD: returned whether the *new* state was COMPLETE.
self.state = states[idx + 1]
return self.state == ScaleUpNewEngineState.COMPLETE  # True at last step
```

The docstring said *"Returns True if the scaling operation is
complete"* — but the implementation returned True only when the
new state happened to be COMPLETE.  In vLLM the
`_progress_*` methods return True when the **state advanced**
(or we're already at COMPLETE); return False when blocked
(waiting on a barrier).

C230 fixes `progress()` to match vLLM: at the start of the call,
if `is_complete`, return True.  Otherwise advance state and
return True.  The skeleton always advances (no real barriers
yet); the real implementation hooks barriers as False
returns — see vLLM
`vllm/distributed/elastic_ep/elastic_state.py:_progress_existing_engine`
where each step that waits on a TCPStore barrier returns False.

### 3. `my_vllm/config/parallel.py` — `data_parallel_size` field

Added `data_parallel_size: int = 1` to `ParallelConfig`.  The
field is required for the elastic EP rebalance decision (which
sizes the DP group) and matches vLLM
`vllm/config/parallel.py:127`.

Also added `clone_with_dp_size(new_dp_size)` helper that returns
a deep-copied `ParallelConfig` with the new size — needed by the
factory so it can build `new_parallel_config` without mutating the
live engine config (matches the construction in vLLM
`vllm/v1/engine/core_client.py:_scale_up_elastic_ep`).

## Runtime Flow

```
Periodic scheduler step (every K iterations or on N% util change):
  signal = EPRebalanceSignal(
      current_dp_size=engine.parallel_config.data_parallel_size,
      kv_cache_utilization=kv_pool.utilization(),
      pending_prefill_tokens=scheduler.num_waiting,
      num_active_requests=len(running),
      elapsed_seconds=engine.elapsed,
  )

  decision = policy.decide(signal)        # pure, no side effects
  if decision.is_hold:
      continue                          # no scale this tick

  state_machine = create_scaling_state_for_decision(vllm_config, decision)
  # state_machine is either ScaleUpExistingEngineState or
  # ScaleDownRemainingEngineState driver; "new" / "removing"
  # workers are managed by separate engine cores on the other
  # side of the same event.

  while not state_machine.is_complete:
      state_machine.progress()         # drive the state machine
      # (real impl: barriers, NCCL collectives, EPLB reshuffle —
      # see vLLM elastic_state.py:_progress_existing_engine)

  # Update ParallelConfig in place (real impl in vLLM
  # elastic_state.py:_update_parallel_config).
  vllm_config.parallel_config = state_machine.new_parallel_config
```

(End-to-end engine-side integration — `_progress_existing_engine`'s
TCPStore barriers + collective_rpc calls — is **not** wired in this
commit.  That's C233 follow-up work: the state machine skeleton here
is purely a control-flow / decision-logic scaffold.  Production
weight-transfer / KV-sync / EPLB-reshuffle hooks defer to a
follow-up that lands when an actual elastic EP deployment is
warranted.)

## Current Capability

* **State machine** — `ElasticEPScalingState` advances through all
  4 prescribed sequences (4 + 9 + 4 + 3 = 20 transitions across
  the 4 sequences; vLLM canon).  `progress()` semantics fixed
  to match vLLM.
* **Control plane** — `EPRebalancePolicy.decide(signal) →
  decision`, with `NoOpEPRebalancePolicy` and
  `ThresholdEPLoadPolicy` defaults.
* **Factory bridge** — `create_scaling_state_for_decision()` and
  `decide_and_create()` map a rebalance decision to a fresh state
  machine (or None for "hold").
* **Cold-start hysteresis** — refuses to scale within
  `min_downtime_seconds` of engine start (avoids reacting to a
  cold-start burst).
* **Custom policies** — `EPRebalancePolicy` is an ABC; test
  proves a 10-line subclass works.
* **`ParallelConfig.data_parallel_size`** — the field that gets
  mutated at runtime; `clone_with_dp_size()` provides a deep copy
  with the new size.

## Current Limitation

* **Engine-side wiring is not implemented.**  The skeleton's
  `progress()` always returns True (no barriers / collectives).
  In vLLM the engine controller drives the state machine via
  collective_rpc to the model executor (which forwards to the
  `elastic_ep_execute` worker method); my-vllm's `MultiprocExecutor`
  doesn't yet implement `collective_rpc`, and the worker doesn't
  have `elastic_ep_execute`.  That's a follow-up.

* **No KPI/threshold tuning.**  The defaults
  (`up_threshold=0.85, down_threshold=0.4, min_downtime_seconds=30`)
  are reasonable starting points but not tuned for any specific
  workload.  In production vLLM this lives in
  `EPLBConfig` and is workload-dependent.

* **No queue-depth signal.**  `pending_prefill_tokens` and
  `num_active_requests` are collected but not used by the default
  policy — they're passed through for custom policies to consume.

* **No expert-load balancing.**  vLLM's
  `vllm/distributed/eplb/policy/default.py` ships 3 expert
  redistribution algorithms (greedy, hierarchical, random) used
  during the EPLB_RESHUFFLE state.  my-vllm's
  `ElasticEPScalingState` advances the state without performing
  an actual reshuffle — the bookkeeping is correct, the
  algorithmic part is a follow-up.

* **Worker-side TCPStore barrier / NCCL weight transfer is not
  implemented.**  Same as above — these are the heavy-lifting
  steps inside vLLM's `_progress_existing_engine` that would land
  when we have a real multi-process deployment to exercise.
