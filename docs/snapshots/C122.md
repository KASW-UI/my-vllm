# C122: Scheduler.schedule — top-to-bottom pipeline

## Goal

Tighten `Scheduler.schedule()` so the hot path reads like nano-vllm's `LLMEngine.step()`:

```
chunk_continue → pull_new → cached_data → assemble
```

LoRA multiplexing, multi-tenant quotas, KV-budget preemption each live in dedicated helpers — not inlined into `schedule()`.

## New Features

### `schedule()` body — 43-line top-to-bottom pipeline

```python
def schedule(self) -> SchedulerOutput:
    self._promote_remote_kv_requests()

    token_budget = self.max_num_batched_tokens
    new_req_datas: list[NewRequestData] = []
    new_blocks: dict[str, list[int]] = {}
    num_common_prefix_blocks: list[int] = []
    preempted_req_ids: set[str] = set()
    scheduled_loras: set[int] = set()

    # 1. Continue chunked prefill for already-running reqs.
    token_budget = self._schedule_chunk_continue(
        token_budget, new_req_datas, new_blocks,
    )

    # 2. Pull new reqs from the waiting queue (FCFS or Priority).
    self._pull_new_requests(
        token_budget=token_budget,
        new_req_datas=new_req_datas,
        new_blocks=new_blocks,
        num_common_prefix_blocks=num_common_prefix_blocks,
        preempted_req_ids=preempted_req_ids,
        scheduled_loras=scheduled_loras,
    )

    # 3. Build cached_data from running reqs NOT in scheduled_new_reqs
    #    (mirrors vllm _make_cached_request_data).
    cached_data = self._make_cached_request_data(new_req_datas)

    # 4. Final assembly.
    return self._assemble_scheduler_output(
        new_req_datas, cached_data,
        num_common_prefix_blocks, preempted_req_ids,
    )
```

### Pipeline helpers

| Helper | Concern | Mirrors |
|---|---|---|
| `_schedule_chunk_continue` | C030 chunked-prefill continuation for running reqs | vllm `Scheduler._continue_chunked_prefill` |
| `_pull_new_requests` | FCFS/Priority drain of `self.waiting` | vllm `Scheduler._get_new_reqs` |
| `_lora_budget_ok` | LoRA multiplexing cap | vllm `Scheduler._lora_enabled` / `_get_reqs_with_lora` |
| `_try_admit_tenant` | Multi-tenant GPU budget + cross-tenant preemption | vllm `Scheduler._try_admit_tenant_req` |
| `_try_allocate_kv` | KV slot allocation + tenant KV budget + preemption | vllm `Scheduler._try_allocate` |
| `_make_cached_request_data` | Cached-req index set (excludes new reqs) | vllm `_make_cached_request_data` |
| `_assemble_scheduler_output` | Total tokens + block copies + SchedulerOutput | (new) |

Each helper either returns success/failure or appends to one of the shared mutable lists (`new_req_datas`, `new_blocks`, etc.) and updates `self.running` / `preempted_req_ids`.

## Runtime Flow

```
Scheduler.schedule()
  ├─ _promote_remote_kv_requests()     # P/D: WAITING_FOR_REMOTE_KVS → WAITING
  ├─ _schedule_chunk_continue(...)      # C030 chunked-prefill continuation
  ├─ _pull_new_requests(...)            # FCFS/Priority drain
  │    ├─ _has_gpu_budget() / _try_preempt_for_gpu_budget()
  │    ├─ _lora_budget_ok()              # C051 LoRA multiplexing
  │    ├─ _try_admit_tenant()            # C120 multi-tenant
  │    └─ _try_allocate_kv()             # C038 KV budget + tenant KV
  ├─ _make_cached_request_data()       # exclude new reqs (C116 fix)
  └─ _assemble_scheduler_output()      # SchedulerOutput
```

## Current Limitation

- File grew from 534 → 669 lines because every helper carries a docstring matching vLLM's style. The intent was readability for study, not minimum line count; the **schedule() body** itself slimmed (150 → 43 lines).
- `_pull_new_requests` is still ~50 lines (the per-req checks: LoRA cap, tenant GPU/KV, KV allocation, chunk accounting). Could split further, but each block is a distinct concern that's clearer in-place.
- `_select_preemption_victims` rebuilds the candidate list every call (no caching). Acceptable at OPT-125m scale; vLLM caches victim selection across calls.
