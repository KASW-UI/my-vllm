# C147: LoRA follow-up — `update_lora_modules()` actually wraps OPT targets

## Goal

Wire the LoRA wrap-from-base-class step so that
`update_lora_modules()` is no longer a no-op stub. After
`init_lora()` returns, every target Linear layer on
`OPTForCausalLM` (`qkv_proj` / `out_proj` / `fc1` / `fc2` in
each decoder block) is replaced with the matching
`*LoRA` wrapper, and the wrappers are registered in
`LoRAModel.lora_modules` so subsequent `set_lora(id)` calls
flow into `BaseLayer.set_lora` correctly.

This is the **third of four** LoRA专项 + follow-up items:

## What C147 did

### 1. `lora/layers/__init__.py` (new)

Re-exports the LoRA layer wrappers from one place:

```python
from my_vllm.lora.layers.base import BaseLayer, LoRAWeights
from my_vllm.lora.layers.base_linear import BaseLinearLayer
from my_vllm.lora.layers.column_parallel_linear import ColumnParallelLinearLoRA
from my_vllm.lora.layers.fused_moe import FusedMoEWithLoRA
from my_vllm.lora.layers.row_parallel_linear import RowParallelLinearLoRA
```

Mirrors `vllm/vllm/lora/layers/__init__.py` (subset).

### 2. `lora/layers/base.py` — `BaseLayer` is now `nn.Module`

**Why**: PyTorch's `nn.Module.__setattr__` only accepts
`nn.Module` instances as child-module replacements.
`LoRAModelManager.create_lora_modules()` does
`setattr(parent, "qkv_proj", ColumnParallelLinearLoRA(...))`
to swap the base Linear for the wrapper — that requires the
wrapper to be a real `nn.Module`.

Change:
- `class BaseLayer(nn.Module)` (was a plain class)
- `__init__` calls `super().__init__()` first, then assigns
  `self.base_layer = base_layer` (auto-registered as child
  module by `nn.Module.__setattr__`).
- Added docstring note explaining the constraint.

### 3. `lora/layers/base_linear.py` — drop redundant `__call__` override

`BaseLinearLayer` defined its own `__call__` that just called
`self.forward(x)`. With `BaseLayer(nn.Module)` now in place,
`nn.Module.__call__` does the same (and additionally wires
forward hooks). The explicit override would have *bypassed*
those hooks. Removed.

### 4. `lora/lora_model.py` — `add_lora()` allocates per-wrapper A/B tensors

C146 stored the `LoRARequest` in `LoRAModel._adapters` but
left every wrapper's `_adapters` dict empty — so
`BaseLayer.set_lora(id)` raised `KeyError("… not registered")`.

C147 extends `LoRAModel.add_lora(...)` to iterate
`self.lora_modules.values()` after registering the request,
and call `wrapper.create_lora_weights(lora_int_id, rank,
in_features, out_features, alpha=1.0)` on each one. Shape is
inferred from the base layer's `input_size` / `output_size`
attributes (provided by my-vllm's parallel Linear layers).

Now `set_lora(id)` succeeds for every wrapper, and
`apply_lora(...)` will compute a non-zero delta when an
adapter is set.

### 5. `lora/model_manager.py` — `create_lora_modules()` + `LORA_LAYER_TYPE_MAP`

New method on `LoRAModelManager` that walks
`self.model.model.named_modules()` (the host `nn.Module`
held by `LoRAModel`) and wraps every target Linear with the
matching `*LoRA` wrapper.

The base-class-to-wrapper-class lookup is centralised in a
module-level constant:

```python
LORA_LAYER_TYPE_MAP: list[tuple[type, type]] = [
    (QKVParallelLinear, ColumnParallelLinearLoRA),
    (MergedColumnParallelLinear, ColumnParallelLinearLoRA),
    (ColumnParallelLinear, ColumnParallelLinearLoRA),
    (RowParallelLinear, RowParallelLinearLoRA),
]
```

Checked in order (most-specific first). All ColumnParallel
variants share `ColumnParallelLinearLoRA` because the LoRA
delta is applied in the same partitioned output space as the
host; RowParallelLinear gets `RowParallelLinearLoRA` which
adds the TP all_reduce.

Replacement mechanic: `setattr(parent_module, "qkv_proj",
wrapper)`. PyTorch's `nn.Module.__setattr__` removes the
old `qkv_proj` from the parent's `_modules` dict (auto-
detaching it), assigns the new wrapper, and — because the
wrapper is an `nn.Module` — `nn.Module.__setattr__` also
auto-registers the old `qkv_proj` as the wrapper's
`base_layer` child submodule.

### 6. `model_executor/models/opt.py` — `SupportsLoRA` class metadata

`OPTForCausalLM` now declares the three class vars vLLM's
`SupportsLoRA` Protocol requires (subset, sufficient for
my-vllm's wrap logic):

```python
class OPTForCausalLM(nn.Module):
    ...
    supports_lora: ClassVar[bool] = True
    embedding_modules: ClassVar[dict[str, str]] = {
        "embed_tokens": "vocab_embedding",
    }
    lora_target_modules: ClassVar[set[str]] = {
        "qkv_proj", "out_proj", "fc1", "fc2",
    }
```

`lora_target_modules` lists every Linear layer in the OPT
decoder block (QKV fused attention, attention output proj,
MLP gate, MLP down) — the canonical LoRA-applicable set for
OPT-style Dense transformers.

The class docstring's "SupportsLoRA inheritance omitted"
caveat has been updated to "SupportsLoRA is declared as
class-level metadata; wrapping happens in
`lora/model_manager.py`".

### 7. `v1/worker/lora_model_runner_mixin.py` — real `update_lora_modules()`

The C146 stub (`return None`) is replaced with a real
implementation that delegates to
`LoRAModelManager.create_lora_modules()`:

```python
def update_lora_modules(self) -> None:
    if not hasattr(self, "lora_model_manager"):
        raise RuntimeError(
            "LoRA not initialised — call init_lora() before "
            "update_lora_modules()."
        )
    n = self.lora_model_manager.create_lora_modules()
    logger.info("LoRA: update_lora_modules wrapped %d modules", n)
    return None
```

And `init_lora()` now calls `self.update_lora_modules()` at
the end so wrapping happens as part of model load —
mirroring vLLM's `load_lora_model()` flow where
`_create_lora_modules` runs before the LoRA-capable runner
returns to the caller.

## Runtime Flow (mermaid)

```mermaid
sequenceDiagram
    participant Caller
    participant Runner as LoRAModelRunnerMixin
    participant Model as OPTForCausalLM
    participant LM as LoRAModel
    participant MM as LoRAModelManager
    participant LAY as LoRA layer wrappers

    Caller->>Runner: init_lora(model, max_loras, max_lora_rank, device)
    Runner->>LM: LoRAModel(model, max_loras, max_lora_rank)
    Runner->>MM: LoRAModelManager(model=LoRAModel)
    Runner->>Runner: update_lora_modules()
    Runner->>MM: create_lora_modules()
    MM->>Model: for name, mod in model.named_modules()
    MM->>MM:   match last name ∈ lora_target_modules
    MM->>LAY: ColumnParallelLinearLoRA(base_layer=mod, ...) or RowParallelLinearLoRA(...)
    MM->>Model: setattr(parent, name, wrapper)  # nn.Module.__setattr__ swaps child
    MM->>LM:   register_module(name, wrapper)
    Note over Model,LAY: model.qkv_proj.base_layer is now the original Linear;<br/>qkv_proj is the *LoRA wrapper

    Caller->>Runner: add_lora(LoRARequest("t", 1, ""))
    Runner->>LM: add_lora(req)
    LM->>LM:   _adapters[1] = req
    loop every wrapper in lora_modules.values()
        LM->>LAY: create_lora_weights(id=1, rank, in_f, out_f, alpha=1.0)
        LAY->>LAY:   _adapters[1] = LoRAWeights(lora_a, lora_b=0, scaling)
    end

    Caller->>Runner: set_lora(1)
    Runner->>LM: set_lora(1)
    loop every wrapper in lora_modules.values()
        LM->>LAY: wrapper.set_lora(1)
        LAY->>LAY:   lora_id_to_loaded_id[1] = 1  # now apply_lora fires
    end
```

## Current Capability

- ✅ `OPTForCausalLM` declares `SupportsLoRA`-style class
  metadata (`supports_lora=True`, `embedding_modules`,
  `lora_target_modules`).
- ✅ `LoRAModelManager.create_lora_modules()` walks the
  host model and replaces every target Linear (qkv_proj,
  out_proj, fc1, fc2 across all decoder layers) with the
  matching `*LoRA` wrapper.
- ✅ `LoRAModelRunnerMixin.update_lora_modules()` is a real
  implementation; `init_lora()` calls it automatically.
- ✅ `LoRAModel.add_lora()` allocates per-adapter A/B tensors
  on every wrapper, so `set_lora(id)` succeeds and
  `apply_lora` computes a delta.
- ✅ `tests/test_C147_lora_wrap.py` covers: classvar
  declaration, wrapping count + class, registry population,
  `set_lora` propagation, post-wrap state_dict
  preservation. **5 tests, all pass deterministically**.

## Current Limitation

- The base-class-to-wrapper map covers
  `(QKVParallelLinear, MergedColumnParallelLinear,
  ColumnParallelLinear, RowParallelLinear)`. A model that
  uses plain `nn.Linear` (no TP) won't be wrapped — my-vllm
  doesn't have such a model currently (OPT uses
  parallel-linear throughout).
- `LoRAConfig.target_modules` filtering is not consulted yet
  — wrapping always uses the model's
  `lora_target_modules`. A future C149+ item can add
  per-config override.
- Per-adapter A/B tensors are allocated with the model's
  default rank + alpha. The actual HF PEFT weight mapping
  (different ranks per module, etc.) is still a stub in
  `LoRAModelManager.load_adapter` (C146); the
  Dense-Linear forward path itself is end-to-end runnable.
- The mixin is **not yet mixed into `GPUModelRunner`**;
  callers must explicitly instantiate a mixin host or
  manually invoke `update_lora_modules`. C148 wires the
  per-step `set_lora` into `execute_model`.
