# C116: gpu_model_runner — V1 unified execute_model pipeline

## Goal

Rewrite `my_vllm/v1/worker/gpu_model_runner.py` so its `execute_model` matches the vLLM V1 pipeline:

```
execute_model(scheduler_output)
  ├─ _update_states       # add reqs / append new blocks
  ├─ _prepare_inputs      # unified: new + cached → flat tensors
  ├─ _prepare_attn        # block_tables + slot_mappings + CommonAttentionMetadata
  ├─ set_forward_context  # global per-step metadata
  ├─ model.forward        # OPTForCausalLM(input_ids, positions)
  ├─ _sample              # hidden_states[logits_indices] → logits → tokens
  └─ _postprocess         # update last_sampled_tokens, append_output_token
```

No more `_execute_prefill` / `_execute_decode` split. The runner is now a single pipeline that takes a `SchedulerOutput`, builds one batch, and produces one `ModelRunnerOutput` — exactly like `vllm/vllm/v1/worker/gpu/model_runner.py:GPUModelRunner.execute_model()`.

This required three coordinated changes (bundled into C116 since they're one logical correction to the hot path):

1. **gpu_model_runner.py** — the rewrite itself. Adds a local `InputBatch` dataclass (mirrors vllm's `v1/worker/gpu/model_runner.py:InputBatch`, subset — no spec-decode, no LoRA multiplexing, no DP). All per-step state flows through `InputBatch`.

2. **scheduler.py — `_make_cached_request_data` semantics**: previously the scheduler built `cached_data` from `self.running` *after* appending the just-scheduled new reqs. That made each new req appear in **both** `scheduled_new_reqs` and `scheduled_cached_reqs` for the same step — the runner consumed it twice and produced 2 sampled tokens per req in step 1. Fix: `cached_data` now excludes req ids in `new_req_ids = {d.req_id for d in new_req_datas}`. Mirrors `vllm/v1/core/sched/scheduler.py:_make_cached_request_data(running_reqs, resumed_reqs, ...)`.

3. **scheduler.py — `update_from_output` advances `num_computed_tokens`**: each sampled token increments `req.num_computed_tokens` by 1. Mirrors `vllm/v1/core/sched/scheduler.py:1240` (`request.num_computed_tokens += num_scheduled_token`). Without this, decode kept writing K/V into the same slot and the same token was sampled every step.

4. **llm_engine.py — `generate()` loop**: previously returned the first `result` matching the req_id, regardless of whether the req was finished. With the scheduler fix, each step produces exactly one sampled token per req, so we now accumulate `last_result` and return only when `finish_reason` is set. Mirrors the conventional vLLM `LLMEngine.generate` blocking-loop pattern.

## New Features

### `GPUModelRunner.execute_model`

Single linear pipeline:

```python
@torch.inference_mode()
def execute_model(self, scheduler_output: SchedulerOutput) -> ModelRunnerOutput:
    if scheduler_output.total_num_scheduled_tokens == 0:
        return _empty_output()

    self._update_states(scheduler_output)
    input_batch = self._prepare_inputs(scheduler_output)
    attn_metadata = self._prepare_attn(input_batch)
    attn_dict = self._build_attn_metadata_dict(attn_metadata)

    with set_forward_context(attn_dict):
        hidden_states = self.model(
            input_batch.input_ids, input_batch.positions,
        )

    sampled = self._sample(hidden_states, input_batch)
    self._postprocess(sampled, input_batch)
    return self._build_model_runner_output(sampled, input_batch)
```

### `InputBatch` dataclass

Mirrors vllm `InputBatch` (subset). Holds:
- `num_reqs`, `req_ids`
- `input_ids` `[num_tokens]`, `positions` `[num_tokens]`
- `query_start_loc` `[num_reqs+1]`, `seq_lens` `[num_reqs]`, `num_computed_tokens` `[num_reqs]`
- `logits_indices` `[num_reqs]` — which token's hidden state feeds the LM head
- `block_table` `[num_reqs, max_blocks]`, `slot_mapping` `[num_tokens]`

### `_prepare_inputs`

Unified prep handles both:
- **New reqs** (prefill, possibly chunked): `chunk = prompt_token_ids[num_computed_tokens:num_computed_tokens + scheduled]`, positions = `range(num_computed_tokens, num_computed_tokens + len(chunk))`.
- **Cached reqs** (decode, single token): `input_ids = [last_sampled_token]`, positions = `[num_computed_tokens]`.

Both write into the same flat `input_ids` / `positions` / `query_start_loc` / `seq_lens` tensors. No prefill-vs-decode fork.

### `_prepare_attn`

Builds `CommonAttentionMetadata`:
- `query_start_loc` (cumsum of per-req scheduled tokens)
- `seq_lens` (total after this step)
- `max_query_len`, `max_seq_len`
- `block_table_tensor`, `slot_mapping`
- `causal = not is_all_decode` (single-token decode queries don't need a causal mask)

### `_sample`

`hidden_states[input_batch.logits_indices]` extracts the per-request hidden state (last prefill token, or the only decode token) → `compute_logits` → `Sampler(logits, all_greedy=True)` → 1 token per req.

## Runtime Flow

```
EngineCore.step()
  ├─ Scheduler.schedule()            → SchedulerOutput
  │    scheduled_new_reqs, scheduled_cached_reqs (no overlap after C116)
  ├─ Executor.execute_model()        → GPUModelRunner.execute_model()
  │    ├─ _update_states
  │    ├─ _prepare_inputs            → InputBatch
  │    ├─ _prepare_attn              → CommonAttentionMetadata
  │    ├─ set_forward_context
  │    ├─ OPTForCausalLM.forward     → hidden_states
  │    ├─ _sample                    → SamplerOutput
  │    └─ _postprocess
  │    → ModelRunnerOutput
  ├─ Scheduler.update_from_output    → EngineCoreOutputs
  └─ OutputProcessor.process_outputs → list[RequestOutput]
```

## Current Capability

- `python run.py`: generates 50 tokens (default max_new_tokens), finishes with `Finish:` (LENGTH cap).
- 191 passed / 55 failed — same baseline as C115. No regressions.
- Each `execute_model` step produces exactly 1 sampled token per scheduled req. Multi-step decode loops correctly: position advances, KV cache fills, sampled tokens differ step to step.
- Scheduler no longer double-schedules new reqs as both new and cached.
- `LLMEngine.generate` correctly waits for `finish_reason` before returning.

## Current Limitation

- `_prepare_inputs` still does Python-level `for req in new_datas:` / `for rid in cached_reqs:` loops; vLLM uses CUDA kernels (e.g. `prepare_prefill_inputs`, `prepare_pos_seq_lens`) in `attn_utils.py`. C117/C118 will move the slot-mapping compute to Triton.
- `_postprocess` updates `request_state` (used by `get_last_token` next step); scheduler updates `req.num_computed_tokens`. The two stay in sync because each step the runner advances the runner-side state by 1 and the scheduler-side state by 1 (in `update_from_output`). No test asserts this invariant yet.
- `_sample` is greedy only (top_k/top_p paths in `Sampler` are dormant); vLLM supports random sampling here.
- `set_forward_context` is called without `cudagraph_runtime_mode` / `batch_descriptor` — CUDA-graph path (C119) will populate them.
