# C015: Introduce v1 Runtime Namespace and EngineCore

## Goal

Establish the `v1/` namespace boundary and rename StateManager → EngineCore.
All legacy execution paths preserved; no internal model changes.

## New Features

- `my_vllm/v1/` namespace created with sub-packages:
  - `v1/engine/` — EngineCore, LLMEngine, exceptions
  - `v1/core/sched/` — SchedulerOutput placeholder (C016 adoption target)
- `Request` class expanded: 11 statuses (vLLM V1 parity), `ConstantList` read-only views,
  `append_output_token_ids()` mutation method, new fields (`arrival_time`,
  `num_computed_tokens`, `block_hashes`, `sampling_params`, `_all_token_ids`)
- `ConstantList` read-only list wrapper from vLLM V1 `v1/utils.py`
- `EngineCore` class replaces `StateManager` (renamed only)
- Old `engine/` files become bridge imports → new v1 paths
- Placeholder data structures: `ModelRunnerOutput`, `SamplerOutput`,
  `SchedulerOutput`, `NewRequestData`, `CachedRequestData`

## Runtime Flow

Same as C014 — per-request execution with HF past_key_values:

```
LLMEngine.add_request()
  → EngineCore.add_request()
      → Scheduler.add_request()

LLMEngine.step()
  → EngineCore.step()
      → Scheduler.schedule()        → list[Request]
      → for req: _prefill()         ← per-request, HF past_key_values
      → for req: _decode_step()    ← per-request, HF past_key_values
      → update_state() / finish
```

## Current Limitation

- Scheduler still returns `list[Request]` (no structured output)
- No batch execution — per-request for loops
- KV Cache still HF `past_key_values` (not physical GPU tensor)
- Scheduler/Worker/Executor/Cache still in old paths (C016-C018 migration)
- `SchedulerOutput` exists as placeholder but not used by Scheduler yet

## Next Stage

C016: Scheduler Output Protocol — Scheduler returns structured `SchedulerOutput`
instead of `list[Request]`, with prefill/decode/finished/new_block channels.
