# C257 — Simple KV Offload 轻量路径 (A-level gap)

**Status**: Closed (Phase 4 v2: 8/10)

## Goal

Wire the lightweight ``SimpleCPUOffloadConnector`` from
``vllm/v1/simple_kv_offload/`` into my-vllm — a standalone scheduler-
side manager + worker-side handler that delegates CPU↔GPU KV cache
transfers to a background-thread copy backend.  Future concrete
storage tiers (NVMe, RDMA-backed PD, etc.) plug into the same C251
``KVConnectorBase_V1`` surface.

This is **separate from** the C255/C256 ``OffloadingSpec`` plug-in
pattern: ``simple_kv_offload`` is a smaller, monolithic connector
that doesn't need the spec / manager / worker ABC hierarchy.

## Runtime Flow

```
Scheduler (per step)
  ├─ schedule() → SchedulerOutput
  ├─ for each req: get_num_new_matched_tokens() → pin CPU hit
  ├─ allocate_slots → KVCacheBlocks
  ├─ for each req: update_state_after_alloc(num_external_tokens=N)
  │     └─ Promote CPU hit into LoadRequestState (touch GPU blocks)
  ├─ build_connector_meta(SchedulerOutput)
  │     ├─ _prepare_*_store_specs → gpu_block_ids, cpu_block_ids
  │     └─ Pack: load_event, load_{gpu,cpu}_blocks, store_event,
  │              store_{gpu,cpu}_blocks, load_event_to_reqs,
  │              need_flush=bool(preempted_req_ids)
  ├─ execute_model() → sampled_token_ids
  └─ update_from_output(KVConnectorOutput)
        └─ update_connector_output(meta)
              ├─ finished_recving → _cleanup_load_request(req_id)
              └─ meta.completed_store_events → aggregate per event_idx;
                 when count >= world_size → _process_store_event
                    └─ _process_store_completion → cached_block_hash_to_block
                                                  .insert(bhash, blk)
                                                  + free CPU + GPU refs

Worker (per step)
  ├─ register_kv_caches(kv_caches) → allocate pinned CPU tensors + init
  │                                 DmaCopyBackend (background thread)
  ├─ bind_connector_metadata(meta)
  ├─ start_load_kv() / wait_for_save() → no-ops (deferred to get_finished)
  ├─ get_finished(finished_req_ids)
  │     ├─ Submit load (CPU→GPU) via launch_copy → enqueue
  │     ├─ Submit store (GPU→CPU) via launch_copy (waits on compute-done)
  │     ├─ Poll _load_events / _store_events for completed event_idx
  │     └─ Returns (None, finished_recving)
  └─ build_connector_worker_meta() → SimpleCPUOffloadWorkerMetadata
                                     {event_idx: 1} since last call

Background thread (DmaCopyBackend._copy_loop)
  └─ Drains SimpleQueue → copy_blocks(src, dst, params) → record event
     on stream → append (event_idx, event) to events_list
```

## Current Capability

* **Scheduler side**: per-step load prep + store prep (eager & lazy
  modes), event-counter monotonic IDs, partial-completion aggregation
  across workers (`world_size`), preemption-flush hook
  (`need_flush`), request-finished defer / immediate cleanup, prefix
  cache reset, KV-event emission via `take_events()`.
* **Worker side**: GPU KV-cache registration with shared-storage
  dedup, pinned CPU allocation (`cudaHostRegister` on CUDA, no-op on
  CPU-only), per-direction copy params, background-thread DMA
  draining, event-based high-water-mark polling, flush-and-sync on
  preemption, idempotent shutdown.
* **Connector surface**: subclasses / wraps the C251
  ``KVConnectorBase_V1`` types (`KVConnectorMetadata` /
  `KVConnectorWorkerMetadata`); `aggregate()` sums completion counts
  per event across workers.
* **CPU fallback**: when CUDA is unavailable the simple-torch copy
  path still works (per-block `tensor.copy_()`); events are still
  recorded and polled.

## Current Limitation

* **`cuMemcpyBatchAsync` not vendored** — the batched DMA path is a
  CUDA 12.8+ driver API.  My-vllm uses a per-block `tensor.copy_()`
  fallback.  Same wire format / lifecycle, lower throughput.
  Production CUDA hosts can swap in `cuMemcpyBatchAsync` by
  implementing the `_resolve_batch_memcpy()` resolver without any
  other code change.
* **ROCm batched DMA not vendored** — `hipMemcpyBatchAsync` requires
  ROCm 7.1+ and the current my-vllm platform layer is CUDA-only.
  The `_resolve_batch_memcpy()` resolver raises `RuntimeError` on
  ROCm.
* **Single-group FullAttention only** — multi-group (FullAttention +
  SlidingWindow + Mamba) is wired through the per-group math but
  only FullAttention cache-hit lookup is exercised end-to-end in C257
  tests.  Hybrid coordinator integration is deferred.
* **Eager + lazy store paths both implemented, lazy mode only used
  in tests** — the lazy cursor-walk offloads near-eviction blocks;
  production wiring (calling `_prepare_lazy_store_specs` vs eager
  based on config) lands with the EngineCore KV-connector dispatch.
* **Prometheus emission deferred** — `take_events()` returns the
  C252 `KVCacheEvent` instances but no Prometheus counter plumbing
  is added in C257.
* **`compute_done` event reuse** — the `_store_compute_done` event
  is recorded fresh each step; vLLM's optimization of reusing the
  same event across steps is preserved (re-allocated on None) but
  not exercised in tests.
